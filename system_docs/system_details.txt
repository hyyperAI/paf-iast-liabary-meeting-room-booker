
A system where there's two different front end and one backend. For my client, one dashboard is for admin and one for user. 

Statement:
A system where students can request allocation of libaary rooms. i.e: 2 discussion rooms. Admin will then accept or reject each student requests after reviewing. All data will be stored in database for future use, no dashboard...

- student flow chart:
Come select date, -> room appear & select 1 or 2-> Select time -> form appear (fill the form and submit request)
- Admin flow chart:
Come select room -> select date -> time appear and select it -> check students request and approve and reject it

# Database structure 

three tables:
1. Rooms: id, no (only 1 & 2), time & date, status ( active, pending, approve )
2. Students: id, registration no, phone number, email, semester, queue no, request status
3. Members: id, room_id (FK) , user_id (FK), name, email

## handling of backend:
Queue logic: Apis for queue logic, that takes in member details and output status of timeslot based on which UI changes
API's : CRUD on each table. logic of calling student's member ( create only api's don't focus on front end at the moment )
 students should be prevented from booking multiple slots on the same day.

## QUEUE SYSTEM:
When a student register request and admin didn't approve, the slot didn't block but instead it's status = pending, and when another student come in and want to register it's go to FIFO queue and starts from 2. 


So first slot is active -> student register application for booking -> queue id = 1, now status -> pending and total_queue_member=0, 
status -> pending & color = yellow -> another student came and register queue id = 2 and toal_queue_member = 1
